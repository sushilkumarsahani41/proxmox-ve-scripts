# Adding a script

The scripts in `ct-lxc/`, `vm/` and `misc/` are generated by `build.sh`.
**Never edit them** — your change will be overwritten on the next build.

## The shape of a service

```
src/
  lib/
    ui.sh          colours, logging, banner, spinner, summary box   (host)
    pve.sh         template resolution, pct create, readiness waits (host)
    main.sh        defaults, arg parsing, create/update/... dispatch (host)
    agent-ui.sh    logging + apt helpers                       (in-container)
  ct-lxc/
    <service>/
      main.sh      help text, DEFAULT_* block, svc_* hooks      -> the host half
      manage.sh    install/update/uninstall/status           -> the container half
```

Two halves, because they run in two different places. `main.sh` runs on the
Proxmox host and knows about `pct` and storage. `manage.sh` gets pushed into
the container and knows about the actual service. They never share code — only
`build.sh` sees both.

`manage.sh` is re-pushed on *every* command, not just create, so an old
container automatically picks up fixes the moment you run `update` against it.

## Steps

1. `cp -r src/ct-lxc/_template src/ct-lxc/<service>` (use `src/vm/` for a VM).
   The directory name becomes the script name: `src/ct-lxc/jellyfin/` builds
   `ct-lxc/jellyfin-lxc.sh`. Directories starting with `_` are skipped.
2. Rewrite the header comment in `main.sh`. It *is* the `--help` output — the
   `# @usage` directive bakes it into the built script.
3. Set `SERVICE_ID`, `SERVICE_NAME` and the `DEFAULT_*` block.
4. Point the `# @embed` line at your own `manage.sh`.
5. Fill in `cmd_install` / `cmd_update` / `cmd_uninstall` / `cmd_status`.
6. `./build.sh <service> && ./tests/smoke.sh`
7. Add a row to the table in `README.md`.
8. Commit **both** the source and the built script.

## Build directives

Only these three, understood in any source file:

| Directive | Does |
|---|---|
| `# @include <path>` | Inlines `src/<path>`, recursively |
| `# @embed <path> AS <fn>` | Inlines `src/<path>` as a function that `cat`s it |
| `# @usage` | Bakes this file's header comment into `pvs_usage_text()` |

Include order in `main.sh` matters: `ui.sh`, then `pve.sh`, then `main.sh`.
`lib/main.sh` reads the `DEFAULT_*` values defined above it and installs no-op
`svc_*` hooks that your definitions below it override.

## Hooks

All optional; the defaults do nothing.

| Hook | For |
|---|---|
| `svc_parse_option` | A service-specific flag. Set `SVC_OPT_SHIFT` to the number of argv entries consumed, return 0; return 1 to reject it as unknown. |
| `svc_install_args` | Fill `SVC_INSTALL_ARGS` with extra args for `manage.sh install`. |
| `svc_summary_lines` | Extra `" label : value"` lines in the closing box. `$1`=ctid `$2`=ip. |
| `svc_post_create` | Anything on the host after install. `$1`=ctid `$2`=ip. |

## House rules

These are the things that make the difference between a script that works on
your box and one that works on someone else's.

- **Never hardcode an architecture.** No `_amd64.tar.gz`. Call upstream's
  installer, or resolve the arch at runtime. Proxmox runs on arm64 too.
- **Never reimplement upstream's install logic.** Download URLs, version
  channels and checksums are theirs to maintain, and they will change them.
- **`update` must be able to roll back.** Back up config/data first, verify the
  service actually came back up, restore and report if it didn't. An update
  that silently bricks something is worse than having no update command.
- **`uninstall` keeps data unless `--purge`.** Deleting someone's config
  because they wanted to reinstall is unforgivable.
- **Status output goes to stderr.** `info`/`ok`/`warn`/`die` all write to
  stderr on purpose: several helpers return values via `x="$(helper)"`, and a
  status line on stdout would be captured into the result and corrupt it
  silently.
- **Don't swallow output.** Use `run_step` — it hides output on success and
  dumps all of it on failure.
- **Never write `(( i++ ))` as a statement.** An arithmetic command whose
  result is 0 exits non-zero, and post-increment yields the value *before* the
  increment — so with `i=0` the first call returns failure and `set -e` kills
  the script. Use `i=$(( i + 1 ))`. Same for `(( n-- ))` reaching 0. Inside
  `if (( ... ))` or a loop condition it is fine, because those are condition
  contexts.
- **Target bash 5** (what Proxmox ships) but **stay parseable on bash 3.2**
  (what macOS ships), so `tests/smoke.sh` runs locally. Notably: no
  `declare -A`, no `readarray`, and use `${arr[@]+"${arr[@]}"}` when an array
  may be empty under `set -u`.
- **Do not trust a local pass as proof.** bash 3.2 and bash 5 disagree about
  `set -e`: `(( i++ ))` with `i=0` aborts under bash 5 and is silently ignored
  under 3.2. A bug of exactly this kind shipped because it passed on macOS.
  CI runs on bash 5 — treat that, not your laptop, as the verdict.
- **Anything gated on `[[ -t 1 ]]` needs a pty test.** Piping a script's output
  disables the spinner entirely, so ordinary checks never execute that code.
  `tests/smoke.sh` allocates a real pty for those paths; extend it rather than
  assuming.

## Testing

`./tests/smoke.sh` runs without Proxmox. It checks that the committed scripts
match `src/`, that everything parses, that `--help` works, that the dispatcher
rejects nonsense, that the *embedded* agent script parses, and that the summary
box lines up. It cannot tell you a container boots — do that on a real host
before you push.

`./build.sh --lint` runs shellcheck over the built scripts if you have it
installed (`brew install shellcheck` / `apt install shellcheck`).
